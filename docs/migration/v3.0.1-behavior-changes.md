# Behavior Changes Since v3.0.1 — Migration Notes

This document describes behavior changes introduced on the `fix/code-review-v3.0.1`
branch on top of the **v3.0.1** release. Several of these changes affect the public
API and have **breaking implications** — see the semver note at the bottom.

---

## Breaking changes

### 1. `Observer.update` gains an `args` parameter

**What changed:** Invoke arguments are no longer stored on the `Event` instance. They
are passed directly as the second parameter to each `Observer.update` call:

```ts
// Before (v3.0.1)
interface Observer {
  update(subject: ObservableSubject): MaybePromise<void>;
}
// read args via: const [subject, ctx] = (event as EventInterface).getInvokeArgs();

// After (next release)
interface Observer {
  update(
    subject: ObservableSubject,
    args?: readonly unknown[],
  ): MaybePromise<void>;
}
// read args via: const [subject, ctx] = args ?? [];
```

**Why:** The old design stored `args` as mutable state on a shared `Event` object.
Two machines built from the same `Process` and triggered concurrently would race —
Machine A's observers could read Machine B's args (or `[]` after B's `finally` reset
the field).

**Migration:** Update any custom `Observer` implementations to accept `args` and read
invoke arguments from that parameter. The `Event.getInvokeArgs()` method is now
**deprecated** and always returns `[]`.

> **This break is silent.** Existing `update(subject)` implementations remain
> assignable in TypeScript (a function with fewer parameters satisfies a target with
> more), so **the compiler will not flag them**. Any observer that still reads
> `getInvokeArgs()` compiles and runs — it just quietly receives `[]`. Audit custom
> observers by searching for `getInvokeArgs`.

**`ObservableSubject.notify` also gains `args?`:** Custom `ObservableSubject`
implementations should forward the `args` parameter to each `observer.update` call.

### 2. `TransitionFrame` gains a `subject` field

**What changed:** A `readonly subject: TSubject` field was added to `TransitionFrame`
(and therefore to `ProposedTransitionFrame`).

```ts
// Before (v3.0.1): TransitionFrame had no subject field
// After (next release): subject is always present
frame.subject; // the domain object whose machine fired this transition
```

**Why:** Without the subject, a `Factory`-registered `StatefulStatusChanger` had no
way to identify which machine's subject to update — every machine wrote to the single
constructor-bound subject.

**Migration:** If you construct `TransitionFrame` objects manually (e.g. in tests),
add the `subject` field. Observers that only read the frame are unaffected.

### 3. `AutomaticTransitionCycleError` fields renamed

**What changed:** The fields `targetStateName` and `visitedStateNames` were replaced:

| Old (v3.0.1)        | New (next release) | Type     |
| ------------------- | ------------------ | -------- |
| `targetStateName`   | `stateName`        | `string` |
| `visitedStateNames` | `hopLimit`         | `number` |

The detection algorithm also changed from first-revisit detection (which rejected
legitimate condition-terminated loops) to a `maxAutomaticHops` hop-count limit
(default `100`, configurable in `StatemachineOptions`). The `Statemachine` constructor
throws `RangeError` if `maxAutomaticHops` is below `1` or non-integer.

**Migration:** Update any catch blocks that access `error.targetStateName` or
`error.visitedStateNames` to use `error.stateName` and `error.hopLimit` respectively.
Existing catch blocks reading the old fields silently receive `undefined` — the
compiler only flags typed accesses.

### 4. Stricter `ProcessBuilder` name validation

**What changed:** One name rule now applies uniformly at declaration time —
non-empty, no leading/trailing whitespace:

- `addState` rejects empty or whitespace-padded **state** names with
  `GraphValidationError` code `"invalidStateName"` (previously unvalidated).
- `addTransition` rejects whitespace-padded **condition** names with code
  `"invalidConditionName"` (previously only empty/blank names were rejected).
- Event-name validation is unchanged (already strict in v3.0.1).

**Migration:** Trim names in state declarations and custom `ConditionInterface`
implementations. Graphs that previously built may now throw at declaration time.

### 5. Conflicting duplicate transitions now throw at `build()`

**What changed:** Re-declaring the same `(fromState, event, toState)` transition with
a **different weight** now throws `DuplicateTransitionError` from `build()`.
Previously the second declaration was silently dropped (first-wins), so a
`WeightTransition` selector resolved on the stale weight. Idempotent re-declarations
(same condition reference, same weight) still dedup silently.

**Migration:** Remove or reconcile conflicting declarations; the error's `conflict`
payload now includes `existingWeight`/`newWeight`.

### 6. Empty-string `initialStateName` now throws

**What changed:** `new Statemachine(subject, process, { initialStateName: "" })`
now throws `StateNotFoundError`. Previously the empty string was falsy and the
machine silently fell back to the process initial state — a subject persisted with a
corrupted/empty state column would silently **restart its workflow from the
beginning**. This also applies to the `Factory` + `StatefulStateNameDetector` path
when a subject's persisted state name is `""`.

**Migration:** Treat the error as the data-corruption signal it is; repair the
persisted state instead of relying on the silent restart.

### 7. Re-entrant `triggerEvent`/`checkTransitions` reject with `ReentrancyError`

**What changed:** Calling `sm.triggerEvent()` or `sm.checkTransitions()` from inside
a synchronous observer, condition, or transition selector of the same machine (i.e.
before the callback's first `await`) now **rejects the returned promise** with
`ReentrancyError` instead of deadlocking. Post-`await` re-entrant calls still
deadlock — that gap requires `AsyncLocalStorage` (Node-only) and is tracked for a
future release.

> **Breaking edge:** the fire-and-forget pattern `void sm.triggerEvent("next")` from
> inside a synchronous callback **worked before** (the op queued and ran after the
> current drain) but now rejects — and because the promise is deliberately not
> awaited, that surfaces as an **unhandled promise rejection** (fatal under Node's
> default policy). Migrate to the `EnqueueContext` passed to after-observers, or
> defer the call out of the synchronous path:
> `queueMicrotask(() => void sm.triggerEvent("next"))`.

### 8. A failed automatic lock release now rejects the operation

**What changed:** With `autoreleaseLock` (the default), if the operation succeeds but
`mutex.releaseLock()` then throws, the caller's promise now **rejects** with the
release error. Previously the failure was swallowed and the promise resolved — while
the underlying distributed lock stayed held, and every subsequent operation silently
piggybacked on it. When the operation itself failed, the operation error still wins
(the release error never masks it). Note the state transition has already committed
by the time the release runs; the rejection signals lock state, not a rollback.

**Migration:** Catch and inspect the rejection if your mutex's release can fail
(e.g. dropped redis/DB connections); the machine's state is still consistent.

## Non-breaking behavior changes

### 9. `StatefulStatusChanger` subject is now optional

The no-arg constructor form `new StatefulStatusChanger()` now reads `frame.subject`
(made possible by change #2 above). The recommended pattern when using `Factory` is
the no-arg form:

```ts
factory.attachAfterObserver(new StatefulStatusChanger()); // writes to frame.subject
```

Passing an explicit subject still works and pins that specific object.

### 10. `OnEnterObserver` fires only for the rest state

**What changed:** The `onEnter` event is now enqueued with `ctx.enqueue(name, context,
frame.toState.getName())`. The `ifStateName` guard means the event is silently skipped
if the machine was carried through that state by an automatic transition in the same
operation and has since moved on.

**Impact:** Code that relied on `onEnter` firing for every transient state in an
automatic-transition chain will no longer see those firings.

## Semver decision point

The following changes are **breaking** and require a version decision:

| Change                                          | Breaking how                                                                                                                                                                                |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Observer.update` signature / `getInvokeArgs()` | **Silent at compile time** — implementations with fewer parameters remain assignable, so existing observers compile unchanged; the break is behavioral (`getInvokeArgs()` now returns `[]`) |
| `TransitionFrame.subject` addition              | Manual frame construction in tests/mocks fails TypeScript compilation until `subject` is added                                                                                              |
| `AutomaticTransitionCycleError` field rename    | Catch blocks accessing `.targetStateName`/`.visitedStateNames` silently receive `undefined` at runtime                                                                                      |
| Stricter build-time validation (#4, #5)         | Previously-building graphs can now throw at `addState`/`build()`                                                                                                                            |
| Runtime guards (#6, #7, #8)                     | Previously-working patterns now throw/reject (empty `initialStateName`; fire-and-forget re-entrant triggers; swallowed release failures)                                                    |

**Maintainer decision required:** four independent breaking surfaces (interface
signature, error shape, build-time validation, runtime guards) point to a **major
release (4.0.0)** under strict semver; a minor (3.1.0) with prominent notes is the
pragmatic alternative if the affected surfaces are judged unused in practice. This
document does not change `package.json` — that is the maintainer's call.
